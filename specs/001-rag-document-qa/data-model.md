# Data Model: RAG Document Q&A

**Input**: [spec.md](./spec.md) Key Entities, [research.md](./research.md)

Two stores hold the data:

- **SQLite** (`data/rag.db`) is the source of truth for documents and chunks, including chunk text.
- **ChromaDB** (`data/chroma`) holds one vector per chunk plus the fields needed for filtering.
- **Disk** (`data/uploads/<document_id>.<ext>`) holds the original uploaded file.

---

## Entity: Document (`documents` table)

| Field | Type | Constraints | Notes |
|-------|------|-------------|-------|
| `id` | string (UUID4) | primary key | Generated by the server |
| `name` | string | not null, 1-255 chars | Display name; defaults to `filename` |
| `filename` | string | not null | Original filename as uploaded |
| `file_type` | enum `pdf` \| `txt` \| `md` | not null | Derived from the file extension |
| `size_bytes` | integer | not null, > 0 | Size of the uploaded file |
| `page_count` | integer | nullable | PDFs only; `null` for TXT/MD |
| `chunk_count` | integer | not null, default 0 | Set when processing completes |
| `status` | enum `DocumentStatus` | not null, default `pending`, indexed | See state machine below |
| `error` | text | nullable | Failure reason when `status = failed` |
| `uploaded_at` | datetime (UTC) | not null | Set on upload |
| `processed_at` | datetime (UTC) | nullable | Set when status becomes `completed` or `failed` |

The stored file path is derived from `id` and `file_type`, so it is not a column.

### State machine: `DocumentStatus`

```
            upload accepted
                  │
                  ▼
             ┌─────────┐
             │ pending │
             └────┬────┘
                  │ background task starts
                  ▼
           ┌────────────┐
           │ processing │
           └─────┬──────┘
        success  │  any error (extraction, chunking, embedding, storage, restart)
       ┌─────────┴─────────┐
       ▼                   ▼
 ┌───────────┐       ┌────────┐
 │ completed │       │ failed │
 └───────────┘       └────────┘
```

- `pending -> failed` is also possible when a restart interrupts a task before it starts.
- `completed` and `failed` are final. There is no reprocessing in this version; delete and re-upload.
- The upload request only validates; full extraction runs in the background, so an extraction error
  on a later page (after the early-exit check passed) also ends in `failed`.
- Delete is allowed in every state. Deleting a `processing` document is not a failure: the
  background task stops cleanly and the document is simply gone.
- Only `completed` documents are searchable.

## Entity: Chunk (`chunks` table)

| Field | Type | Constraints | Notes |
|-------|------|-------------|-------|
| `id` | string (UUID4) | primary key | Generated by the server |
| `document_id` | string | FK -> `documents.id`, `ON DELETE CASCADE`, indexed | Owning document |
| `chunk_index` | integer | not null, >= 0; unique with `document_id` | Order within the document, 0-based |
| `text` | text | not null, non-empty | Chunk content |
| `page_start` | integer | nullable, >= 1 | 1-based PDF page where the chunk starts; `null` for TXT/MD |
| `page_end` | integer | nullable, >= `page_start` | PDF page where the chunk ends; equals `page_start` for single-page chunks; `null` for TXT/MD |
| `token_count` | integer | not null, 1-`chunk_size` | Counted with the embedding tokenizer |
| `embedding_id` | string | not null, unique | Id of the vector record in Chroma (equal to `id`) |

`embedding_id` is kept as its own column so the link to the vector store is explicit, even though
the current implementation uses the chunk id for both.

Chunks may cross page boundaries (research.md section 1), which is why a page *range* is stored.
`page_start` and `page_end` are either both set (PDF) or both `null` (TXT/MD).

**SQLite note**: SQLite ignores foreign keys unless `PRAGMA foreign_keys = ON` is set on every
connection. The engine sets it on connect so `ON DELETE CASCADE` works; the ORM relationship also
uses `cascade="all, delete-orphan"`.

## Vector record (ChromaDB collection `chunks`)

| Field | Value |
|-------|-------|
| `id` | `chunks.embedding_id` |
| `embedding` | 384 floats, normalized |
| `metadata.document_id` | `chunks.document_id` - used for filtering and deletion |
| `metadata.chunk_index` | `chunks.chunk_index` |
| `metadata.page_start` | `chunks.page_start` (omitted when null; Chroma metadata cannot be null) |
| `metadata.page_end` | `chunks.page_end` (omitted when null) |

Collection distance: cosine. Text is not stored in Chroma; search returns ids and distances, and
the chunk text and document name are loaded from SQLite.

---

## Relationships

```
Document 1 ──── * Chunk 1 ──── 1 Vector record
   │
   └── 1 original file on disk
```

Deleting a document removes, in order: Chroma vectors (by `document_id`), the SQLite document row
(chunks cascade), and the file on disk. Removing vectors first means a crash midway can leave a
document without vectors, never vectors without a document.

## Out of scope

**Conversation** (optional in the brief) is not part of this version. If added later: a
`conversations` table (`id`, `created_at`) and a `messages` table (`id`, `conversation_id`,
`role`, `content`, `created_at`).
